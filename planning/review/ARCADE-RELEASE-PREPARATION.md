# ArcadeO production preparation

This is preparation, not deployment evidence. No Cloudflare account ID, real Arcade D1 UUID, production origin, deployed KDF measurement or physical phone is available in this execution. Keep those gates explicit. Do not use another project's database or change global Wrangler login.

1. In the existing Cloudflare login, select/create the owner-requested Arcade account. Copy its account ID and create the ArcadeO-only D1 database after release authorization. Existing account membership is not evidence that the intended new account is ready.
2. Set `ARCADE_CF_ACCOUNT_ID`, `ARCADE_D1_DATABASE_ID` and `ARCADE_PRODUCTION_ORIGIN` in this shell. The origin is the exact HTTPS origin used by both players. Run `node scripts/prepare-release.mjs --check`, then `node scripts/prepare-release.mjs`. The generated `.local/wrangler.arcade-production.json` explicitly targets that account and database; it does not deploy or invoke cloud tools.
3. Inspect the prepared config. Keep `ENVIRONMENT=production`, exact `ALLOWED_ORIGIN`, the SQLite Durable Object binding/migration and the current compatibility date. Production must reject wildcard Origin. Store a randomly generated CSRF secret of at least 32 characters with `npx wrangler secret put CSRF_SECRET --config .local/wrangler.arcade-production.json`; use the interactive prompt. Never place secrets in configuration, reports, screenshots or committed SQL.
4. Before authorized production changes, export the Arcade database using `npx wrangler d1 export DB --remote --config .local/wrangler.arcade-production.json --output .local/arcade-before-release.sql`. Protect this file: it contains private account/history data. Record the previous deployed Worker version and retain its source/build. D1 backup does not back up authoritative Durable Object state; leave its namespace and match identities intact.
5. Apply additive migrations using `npx wrangler d1 migrations apply DB --remote --config .local/wrangler.arcade-production.json` only after authorization. Migration 0004 retains history and backfills interruption only from explicit saved result metadata. Do not delete/reset the database or namespace.
6. Provision exactly A/B with `scripts/provision-accounts.mjs`, supplying passwords through environment variables and protecting `.local/accounts.sql`. Account inserts use `ON CONFLICT(id) DO NOTHING`; existing credentials/preferences stay intact. Inspect existing account identities before inserting; never use provisioning to reset passwords. Apply SQL only to the verified Arcade target after authorization. Do not commit it.
7. Run final local checks and an authorized Worker dry run against the prepared config. Deploy only with explicit release authorization. Then verify HTTPS cookie Secure/HttpOnly/SameSite behavior, exact Origin/CSRF rejection, local-account isolation, deployed KDF CPU/memory and two-account UI-only Remote completion on the actual production URL.
8. On phone and PC sign out separately, sign in as different A/B accounts and verify their displayed names. Test Remote invitation, both Ready, alternating moves and finish without reload. Check Pixel/iPhone browser and installed PWA Back/Leave/Resume, suspension/reconnect, keyboard/safe areas and reduced motion. Browser-sized contexts are local emulation only.

Rollback restores the previous compatible Worker version/build while retaining the additive schema and Durable Object namespace. Never roll back by dropping migration columns or restoring a D1 export over newer accepted DO state. For an incident, pause release changes, preserve evidence and reconcile projections from saved authority. Retain any D1 backup privately for recovery of supported data only.
