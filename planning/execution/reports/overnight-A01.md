## Findings for the lead

1. **Critical — disconnect enforcement contradicts the owner policy.** `worker/matches/match-do.ts` derives a 30-minute forfeit from transient in-memory `seatLastContact`, serializes a scored resignation, adds a result projection, and schedules alarms for the forfeit (`getDisconnectEligibility`, `checkAndEnforceDisconnect`, `scheduleEarliestAlarm`). `handleAction`, `alarm`, snapshot fetch, and socket setup paths call the enforcement helpers. A process/DO restart also resets the contact timestamps, so the policy is both incorrect and not durable. Remove disconnect eligibility and terminalization from all ingress/alarm paths. A disconnected player must leave the match active, retain its accepted state, and see submissions paused on the client. Explicit resignation remains a deliberate user action.

2. **Critical — deliberately saved matches still expire.** `match.leave-save` writes `expiresAt = serverTime + 72h`; `match.resume` rejects after that timestamp; expiry checks mutate saved snapshots into terminal `expired`, project them, release their slot, and schedule alarms. Remove the write, resume rejection, expiry enforcement calls, and expiry alarm scheduling. Treat a non-null `expiresAt` in an old *still-saved* snapshot as legacy metadata and ignore it. Preserve already terminal `expired` records as terminal history; do not reactivate them. Keep DO snapshot columns/read support during compatibility; no destructive DO migration is needed.

3. **Critical — the server view cannot report accepted invitation/readiness state.** `SnapshotData` contains `readiness` and `controller.invitationAccepted`, and handlers update those values on Accept/Ready, but `buildFilteredView` omits both. Its `participants.*.ready` values come from participant metadata and are not the canonical state. Consequently the client cannot reliably distinguish invitation acceptance from each account's accepted Ready action. Add the canonical accepted facts to `FilteredMatchView` (for example `invitationAccepted` plus `readiness: { A, B }`) and populate every view from the DO snapshot. Keep participant names/ready only as display fields if compatibility requires them. This shared protocol change is lead-managed.

4. **High — viewer control can go stale on the initiating account.** The DO already computes viewer-specific `controller.isController` in `buildFilteredView`, including account-keyed Sudoku `playerControllers`. `handleAcceptedReply` and `handleRejectedReply` update `view` without updating `controllerStatus`; receipt/secret-recovery reconciliation also replaces `view` without consistently updating it. Socket event/snapshot handlers do refresh it. Derive the client capability from each incoming latest view in one helper and apply it on snapshot, accepted/rejected, receipt, secret recovery, takeover/control, and reconnect paths. Preserve independent A/B Sudoku generations; global `controllingAccountId` changes must not imply that the other Sudoku account lost control.

5. **High — transport failure and game rejection share unsafe assumptions.** In `src/sync/match-session.ts`, HTTP fallback assumes every response has JSON and a `status`, and only rejected replies clearly use `latestView`. A 401/403/404/409/429/503, malformed JSON, or timeout can become an opaque parse/error path. For uncertain board actions the code does retain the same pending action ID and checks its receipt before retry, which is the correct invariant; preserve that behavior. Introduce/retain a typed transport result/error boundary separate from `ActionResponse`, keep the pending envelope intact, and surface HTTP status/code/latest view when present. Never turn an unknown acceptance into a newly generated action ID. Secret recovery remains its separate atomic endpoint.

6. **High — interrupted Sudoku Duel is not end-to-end projected for eligibility.** `SudokuState.interrupted` is set on the accepted `match.leave-save`; the Duel completion result includes `details.interrupted`, but current `ProjectionPayload` does not expose a top-level eligibility/interruption fact and `sudokuRecords()` omits it. `projectSudokuRecord` cannot mark a record interrupted, and `worker/api/records.ts` includes all qualifying shared results when calculating totals/streaks and does not filter interrupted Sudoku best-time rows. Add an explicit monotonic `interrupted`/eligibility fact to terminal result/outbox and `SudokuRecordParams`; persist it in an additive D1 migration and use it for competitive summaries and best-time queries. Keep interrupted completion rows visible in history and completed-puzzle markers. Do not infer old interruption where historical metadata is absent.

## Mode and control invariants

| Actual mode | Accepted start/readiness | Controller and recoverability invariant |
| --- | --- | --- |
| Seven games, Remote | Waiting invitation: B accepts, then A and B each Ready; both accepted readiness facts move lifecycle to active. | A and B control their own authenticated account/device; turn/round/legal-action guards decide which account may submit a move. Disconnect, refresh, background, or offline never changes result/lifecycle. Offline pauses input; reconnect masks secrets and reconciles the same pending ID/receipt before re-enabling. |
| Seven games, Together | Creation is active and both logical seats are ready. | The designated account/session controls the shared device. Seat/chooser comes from server state. Takeover increments generation; only explicit takeover changes control. Save/resume uses the single controller. |
| Sudoku Practice | Creation is active for its single participant; no second-account readiness. | Only that participant's current session generation edits. Ordinary refresh/background/offline retains competitive elapsed time unless Practice was explicitly paused. A saved attempt pauses by the accepted save operation and is resumed by its owner. |
| Sudoku sender Challenge, unpublished | Sender attempt is active and solo. | Sender alone controls it. Completion creates the immutable sender result; publication is a distinct later action. Resume must not require B. |
| Sudoku Challenge, published receiver | Waiting until receiver accepts; accepted receiver begins an independent attempt. | Receiver controls its own attempt. Sender's completed attempt stays immutable; sender completion must not be conflated with the receiver's readiness/resume. |
| Sudoku Live Duel | Invitation accepted and both Ready before scheduled activation. | A/B hold independent account-keyed controller generations and edit private progress concurrently. A's takeover cannot revoke or announce a takeover to B. Save marks interruption monotonically; both required acknowledgments resume saved Remote/Duel. Completion/history remains visible, but interrupted Duel is excluded from competitive wins/streaks/best times. |

For every mode, a board action is enabled only when the latest accepted lifecycle is active, its action is in `legalActions`, the viewer has the mode-correct control, connectivity/input state permits writes, and no incompatible pending action exists. Recovery actions are exceptions to board gating: invitation Accept/Decline/Ready must work while waiting; Resume must work while saved; Back remains available offline. `match.leave-save` and `match.resume` already exist in protocol/DO (`shared/protocol/types.ts`, `worker/matches/match-do.ts`) but UI discovery currently filters Home and game-detail lists to only `active`/`waiting` (`src/app/pages/home-page.tsx`, `src/screens/game-detail.tsx`).

## Motion, transport, interruption interfaces

- `useAcceptedMotion` in `src/components/accepted-motion.ts` is correctly keyed to a new accepted event and deduplicates the currently seen event. It cancels prior animations on a new event, null event, and unmount. It has no explicit settlement handle for snapshot reconciliation, route/back navigation, backgrounding, offline, or live `prefers-reduced-motion` changes. A08 should provide one shared settlement/cancellation path; settlement should render the latest accepted board immediately, and no animation callback may advance authoritative game state.
- `ActionResponse` (`shared/protocol/types.ts`) models accepted/rejected game outcomes; transport failures should stay outside this union. Latest views already carry the data needed to re-derive viewer capability. Keep unknown-acceptance receipt recovery by original action ID in `MatchSession`.
- Sudoku `interrupted?: boolean` exists in `shared/games/sudoku/types.ts` and is set by the authoritative save branch. Make it monotonic (`existing || true`); normal refresh/offline/reconnect must not set it. Resume clears the gameplay pause but never clears interrupted.
- Existing D1 schema ends at `migrations/0003_library.sql`. Lead owns the new additive migration and shared protocol/schema lease. Recommended next migration: `0004_sudoku_interrupted.sql` adding explicit default-false interruption metadata to `results` and `sudoku_records`, preserving old rows. Backfill only from supported existing result JSON metadata (`details.interrupted === true`); leave unknown history at false/unknown policy rather than guessing. The projector/upsert must monotonically retain true. `getCompletedPuzzleIds` and history remain inclusive; competitive record/streak/best-time calculations filter interrupted rows. Existing results `details` should remain intact.
